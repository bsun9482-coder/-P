# 代码规范复核（2026-09-23）

> 视角：这次不看功能对不对，只看**这份代码写得规不规范、像不像专业后端**。
> 本轮**只检查、只记录，没有改动任何代码**。
>
> 复核对象：后端 `app/` 37 个 py（6444 行）、`tests/` 18 个 py（3957 行）、
> 前端 `frontend/src/` 20 个文件（约 3500 行）、`pyproject.toml`、
> `.github/workflows/`、`deploy/`、`BUG_REPORT.md`。

## 一句话结论

**它不是"乱写的代码"，它是"一路修 bug 修出来的代码"。**

该有的东西基本都有——分层目录、类型标注、文档注释、CI、测试、数据库迁移，
比大多数个人项目规矩得多。但每一样都只做到"看起来够用"就停了：
**分层只搭了架子、类型标了却没人检查、注释里引用的编号自己都对不上、
前端完全没人看管、样式纪律有洞。**

下面按"对以后维护影响多大"排序。

---

## 第一部分：做得确实像样的地方（先说好的）

不吹不黑，这些是专业做法：

1. **目录分层清楚。** `routers/`（收发请求）、`stores/`（存取数据）、
   `services/`（通用能力）、`core/`（基础设施）、`agent/`（面试大脑）、
   `crawler/`（抓题）。新人能一眼知道该往哪放代码。

2. **数据库设计是认真的。** 外键带级联删除、唯一约束、该建的索引都建了；
   全文检索用的是 FTS5 的"外部内容表 + 三个同步触发器"——这是 FTS5 的
   标准用法，很多人会写错；登录令牌只存哈希不存明文；密码是加盐的 PBKDF2。
   每一列还都写了中文注释说明用途。

3. **类型标注 90%、文档注释 75%。** 而且注释多数在讲"为什么这么做"
   而不是"这行代码在干嘛"——这是好注释。

4. **有 CI，而且是两段式。** `lint` 段跑 ruff 检查和格式检查；
   `test` 段跑单元测试，Python 3.10/3.11 各跑一遍，还设了 15 分钟超时
   （注释里写了"曾因某个用例挂死占满 6 小时"，说明是真踩过坑才加的）。

5. **代码里没脏东西。** 全项目只有一个 TODO 类标记（`coach.py:34` 的
   `ponytail:`），没有 `FIXME`，**没有一处裸 `except:`**（这是低级错误的典型标志），
   没有调试用的 `print` 残留在服务代码里。

6. **数据库迁移有版本管理**（`PRAGMA user_version`，当前 8），
   而且 v7、v8 的迁移还写了事务，注释解释了为什么不能用 DROP+RENAME 的写法。

7. **依赖管理规范。** 依赖只写在 `pyproject.toml`，有版本区间，
   开发依赖单独分组，命令行入口也登记了。

**基线：`pytest` 233 通过 / 2 跳过，`ruff check .` 干净，CI 是绿的。**

## 第二部分：不规范的地方

### 问题 1：`app/core/db.py` 是个 1328 行的"万能抽屉"

**占整个后端代码量的五分之一，一个文件塞了 6 个互不相干的领域：**

| 装在这个文件里的东西 | 大概占比 |
|---|---|
| 题库（题目存取、标签、搜索、全文检索） | 最大 |
| 面试会话（会话、问答记录、状态） | 大 |
| 收藏 | 小 |
| 用户 + 登录令牌 + 语音临时票据 | 中 |
| 定制面试 | 小 |
| **爬虫的清洗状态、分类抓取记录** | 中 |

最后那一类是明显的越界——`list_pending_semantic_clean`、`mark_clean`、
`clean_stats`、`is_category_fetched` 这些是**爬虫自己的业务状态**，
不该塞在最底层的数据库文件里。

**更尴尬的是**：这个项目**已经有 `stores/` 这一层**（`session_store`、
`voice_store`、`auth`），但打开一看，它们只是"转手壳子"——比如
`voice_store.py` 连函数带注释一共 26 行，四个函数全都是一行转发给 db.py。

> 等于说：**他知道要分层，把架子搭好了，但真正的代码还是堆在同一个抽屉里。**

**为什么这算问题：** 以后任何一处改动都要在 1328 行里找位置；
两个人同时改题库和会话，几乎必然改到同一个文件、产生冲突；
新人想了解"会话数据怎么存的"，得先跳过 1000 行题库代码。

### 问题 2：`agent/coach.py` 里三对"同一件事写了两遍"

面试状态机里，"一句一句往外吐"（流式）和"一次性给完整回复"（同步）
是两套入口，作者就**把同一套逻辑抄了两份**：

| 同步版 | 流式版 | 内容重合度 |
|---|---|---|
| `_handle_mock`（57 行） | `_handle_mock_stream`（94 行） | **59%** |
| `_ask_next_question`（34 行） | `_ask_next_question_stream`（57 行） | **71%** |
| `_finish_report`（22 行） | `_finish_report_stream`（34 行） | **64%** |

**关键问题在于：两边不一样的部分，正好是"出错了怎么收场"。**
流式版每一步都做了"先存个快照，出错就退回去"；同步版没做
（同步版靠在最外层包了一层补救）。

**为什么这算问题：** 每次改面试流程，都得记住"改两遍"。
漏改一边，就会出现"文字版正常、语音版出错"这种查起来很痛苦的问题。
项目里已经出现过这种情况——`coach.py` 里多处注释写着
"与流式入口一致"，说明是**后来发现不一致，又回头补的**。

### 问题 3：收发请求的文件里塞了业务逻辑

`routers/` 本该只干"接请求、给响应"两件事。但实际：

- `routers/session.py` 的 `chat` 函数 **91 行**：里面做了限流、并发控制、
  装载会话、生成回复、把回复塞进展示历史、存库、组装 SSE 事件。
- `routers/custom.py` 的 `generate` 函数 **84 行**：里面做了
  "生成题目 → 存一份给语音用 → 归档旧会话 → 建新会话 → 发 6 种不同事件"
  这一整套编排。

**为什么这算问题：** 想知道"定制面试到底发生了什么"，不能只看业务层，
得翻到收发层的函数里读；这些逻辑也没法在业务层被复用或单独测试。

| 函数 | 长度 | 里面干了什么 |
|---|---|---|
| `db._migrate` | **137 行** | 8 个版本的迁移，一串 21 个 `if` |

想单独调其中一件（比如只改"切句子"的规则）几乎不可能，
得在 131 行里小心地绕开其它 5 件的状态。

### 问题 5：接口"返回什么"没写清楚（21 个接口，0 个写了）

看一眼统计：

```
auth.py       POST /register        ✗ 没声明返回什么
auth.py       POST /login           ✗
...
questions.py  GET  /questions       ✗
questions.py  GET  /favorites       ✗
session.py    GET  /session         ✗
session.py    POST /chat            ✗
...
共 21 个路由，声明返回值结构的 0 个 (0%)
```

收到的数据（请求体）都有格式定义，**发出去的数据全靠"自由发挥"**。

返回值形状还不统一，一共出现四种写法：

```
{"ok": True}                                    ← 只回个"成功"
{"items": [...], "favorite_ids": [...]}         ← 列表带附带信息
{"ids": [...]}                                  ← 光一个数组
{"token": ..., "user": {...}}                   ← 直接返回用户对象
```

**为什么这算问题：**
1. 自动生成的接口文档里，这些接口的"返回什么"是空的，前端没法照着写。
2. 前端只能靠**读后端源码 + 手抄**来对齐，一改就断。
3. 这就是为什么会写出 `s.report_data || null` 这种"战战兢兢的兜底"
   ——因为前端根本不知道这个字段会不会出现。

### 问题 6：代码注释在引用一套"查不到的编号"（93 处）

代码注释里有 **93 处**写着 `bug #N`（散在 20 个文件里），
而项目里同时存在一份 `BUG_REPORT.md`，用的是 `BUG-NN`。

**两套编号数字范围几乎一样（都是 1~37），含义却对不上。** 举几个实例：

| 位置 | 代码注释说 `bug #31` 是 | `BUG_REPORT.md` 说 `BUG-31` 是 |
|---|---|---|
| `app/core/db.py:294` | 迁移非事务 → **对得上** | 迁移非事务 |
| `app/crawler/javaguide.py:75` | source_id 不稳定 → **对不上** | 迁移非事务 |
| `app/stores/auth.py:11` | 语音临时票据认证 | — |
| — | — | `BUG-23` = ASR 无限重试 |

也就是说：

- `bug #31` 这一个编号，在项目里**同时指两件完全不同的事**
  （迁移非事务 / source_id 不稳定）。
- `bug #23` 在代码里是"语音票据"，在报告里是"ASR 无限重试"。
- 有些又能对上（`bug #30` 两边都是"报告解析章节误激活"）。

**为什么这算问题：** 注释失去了"能查证"的意义。
以后有人看到 `（bug #23）` 去翻报告，翻到的是一条毫不相干的记录，
会以为是注释写错了。而 `BUG_REPORT.md` 顶部的状态总览
也已经和代码现状不符了。

### 问题 7：前端是"无人看管区"

后端和前端的管理水平完全不对等：

| | 后端 | 前端 |
|---|---|---|
| 代码量 | 6444 行 | 约 3500 行 |
| 自动测试 | **3957 行** | **0** |
| 格式检查 | ruff + CI 门禁 | **没有** |
| CI 是否覆盖 | 是（两段） | **否，CI 根本不碰前端** |

具体：`frontend/package.json` 里的命令只有 `dev` / `build` / `preview`，
**没有 lint 命令，也没有测试命令**；开发依赖只有 vite 和 Vue 插件两个。

**为什么这算问题：** 前端改坏了，流水线一点反应都没有，
只能靠人肉点。而且前端已经有三个大文件需要盯：

- `useVoiceCall.js` **819 行**（语音引擎：状态机、音频队列、打断、降级全在一起）
- `ChatView.vue` **614 行**
- `QuestionBankDialog.vue` **484 行**

### 问题 8：样式"单一来源"的纪律有洞

项目专门写了一个测试来守住"品牌色只能定义在一处，组件里不许写死"
（`tests/test_css_discipline.py`，3 个测试）。**但这个守卫只管三个品牌主色。**

结果就是：

1. **`main.css` 的 `:root` 里又写死了 7 个衍生色**
   （`--el-color-primary-light-3: #e39b7c`、`--el-color-primary-light-5: #edbb9f`……），
   这些是品牌色的"浅色版"，相当于品牌色被拆散到了多处。
2. **组件里还有 6 处直接写死的十六进制颜色**：

   | 写在哪个组件 | 颜色 | 说明 |
   |---|---|---|
   | `ReportPanel.vue` | `#f1ece3` ×2 | 分数环底、进度条底 |
   | `ReportPanel.vue` | `#d9a441`、`#e6bb6d` | 低分进度条渐变 |
   | `QuestionBankDialog.vue` | `#f9e6d8` | 选中行底色 |
   | `QuestionBankDialog.vue` | `#faf3e8` | 骨架屏高光 |

   注意 `#d9a441` —— 它**就是 `--warning` 的值**，
   组件里却写死了，没有引用令牌。

守卫之所以放行，是因为规则只盯主色。**纪律有，但守的不是全部。**

### 问题 9：建表语句看不出表的真面目

`app/core/db.py` 顶部有一段 `SCHEMA` 建表语句，看着挺全。
但对比数据库里的实际结构：

```
questions   建表语句 12 列 / 实际 15 列
    ↑ 只有读完 8 次迁移才知道还有: clean_status, clean_version, cleaned_at

sessions    建表语句 10 列 / 实际 14 列
    ↑ 只有读完 8 次迁移才知道还有: state_json, status, updated_at, user_id
```

`sessions` 表少的那 4 列里，**包括最重要的两个**：
`status`（这场面试是进行中还是已归档）和 `user_id`（这场面试属于谁）。
而这两个字段恰恰是代码里到处在用的。

**为什么这算问题：** 想知道"会话表到底有哪些字段"，
不能看建表语句，必须把 137 行的迁移代码从头读到尾。新人第一次看必踩。

### 问题 10：测试是按"第几批修的"归档的，不是按"测什么"归档的

`tests/` 里有两套完全不同的组织方式混在一起：

- **按批次**：`test_bugfix_batch.py` 一个文件 **623 行**，
  装的是"第 1~4 批修复"的用例，内容横跨**认证令牌、限流、聊天流、
  样式纪律、报告解析、爬虫乱码**——完全不相关的领域挤在一个文件里。
  里面有 **22 处** `bug #N` 引用。
- **按模块**：`test_coach.py`、`test_voice.py`、`test_crawler.py` 这种。

**另外：`tests/` 下没有 `conftest.py`（公共测试准备文件）。**
后果是每个测试类都自己抄一遍准备工作：`setUp` 一共 **25 个**，
手写"换一个临时数据库路径"的补丁 **21 处**。

**为什么这算问题：** 想查"题库筛选的行为是怎么被保证的"，
得先在两个体系里各找一遍。准备工作抄 21 遍，
改一次测试基建（比如换测试库方式）就要改 21 处。

### 问题 11：空壳和死配置还挂在系统里

| 位置 | 情况 |
|---|---|
| `app/crawler/nowcoder.py` | **空壳**：`fetch()` 直接 `return []`，但依然登记在 `run.py` 的抓取列表里，每次跑爬虫都白跑一遍 |
| `app/ui/` | 这个"包"里只剩 2 行 `__init__.py` 和两张图片（早期界面的残留），却还挂在 `pyproject.toml` 的打包清单里 |
| `config.WEB_URL` | 默认值还是 `http://localhost:8501`（早就退役的旧端口），**全项目零引用** |
| 算法题的说法 | **三处互相矛盾**：注释说"算法题已从题库移除"，但六阶段第 2 阶段专门考算法；标签池里还留着 10 个 `算法-*` 标签；而算法题的唯一来源默认是关闭的 |

**为什么这算问题：** 这些不算故障，但会让读代码的人反复确认
"这个东西到底是有用还是没用"，纯消耗信任。

### 问题 12：打包清单是手动维护的

`pyproject.toml` 里包清单是**硬编码的一串**：

```toml
packages = ["app", "app.agent", "app.crawler", "app.core",
            "app.services", "app.stores", "app.routers", "app.ui"]
```

**以后加一个子包（比如 `app.workers`），忘记了加这一行，
本地跑得好好的，装出来的包就是缺文件的。** 这类问题很难查。

## 第三部分：整体评价

打个比方：

> **这个项目的骨架是专业工程师搭的，内脏是被长期赶工填满的。**

证据就是那 93 处 `bug #N`。一个从头设计、边写边想的项目，
不会在注释里到处引用"第几号缺陷"；只有**在一个已经跑起来的系统上
反复打补丁**，才会有这种痕迹。

具体来说，水平是分层的：

| 方面 | 水平 |
|---|---|
| 目录结构、命名 | **专业** |
| 数据库设计（约束/索引/全文检索/迁移） | **专业** |
| 密码与令牌处理 | **专业**（令牌只存哈希、PBKDF2 加盐） |
| 提交规范、CI、依赖管理 | **专业** |
| 注释与文档 | **良好**（讲原因、有中文说明） |
| **代码组织（文件职责、函数长度）** | **不合格** |
| **重复代码（同一件事写两遍）** | **不合格** |
| **接口契约（返回什么没声明）** | **不合格** |
| **前后端管理对等性** | **不合格**（后端有门禁，前端裸奔） |
| **可追溯性（注释编号、测试组织）** | **不合格** |

一句话概括这些"不合格"的共同点：
**每一项都知道该怎么做，都做了个开头，但都没做到能被人依赖的程度。**

## 第四部分：建议的方向（按性价比排序，供你挑）

### 方向一：把注释里的编号理清（对应问题 6）
 **最该先做，零风险。**
把 93 处 `bug #N` 换成能查到的说法（要么统一到 `BUG_REPORT.md` 的编号，
要么干脆把"为什么这么写"直接讲出来，不引用编号），并把报告顶部的
状态总览更新到与代码一致。**纯改注释，不动一行逻辑。**

### 方向二：把接口"返回什么"补上（对应问题 5）
给 21 个接口加上返回值声明。**只在函数上一行加声明，不改内部逻辑**，
加完自动生成的接口文档就完整了，前端也有据可依。
成本小、长期收益大。

### 方向三：扫掉空壳和死配置（对应问题 11 + 12）
删掉空的牛客网适配器、清理 `app/ui/` 残留、删掉没人用的 `WEB_URL`、
统一"算法题到底要不要"的说法、把打包清单改成自动收集。
**都是删东西和改配置，不碰业务。**

### 方向四：给前端补上守卫（对应问题 7）
加一个格式检查工具 + 一条 `npm run lint`，并让 CI 也构建一次前端。
**不改任何业务代码**，但从此前端改坏了流水线会红。

### 方向五：把数据库那个大文件拆开（对应问题 1 + 9）
按领域拆成几个文件，并把建表语句补全到"一眼能看到最终结构"。
收益很大，但要动所有引用它的地方，**影响面最广，建议排在后面**。

### 方向六：消掉重复的三对实现（对应问题 2）
把面试状态机的"同步版 / 流式版"合成一份。
**这是所有方向里风险最高的**——碰的正是最容易出 bug 的地方，
而且必须先有足够测试兜底。**如果要做，建议放最后，并配一批新测试。**
